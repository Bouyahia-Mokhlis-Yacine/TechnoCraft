# SATIM web application

Use the [repository instructions](../README.md) to generate the sealed competition snapshot and install the locked dependencies. The production app runs with Node.js 20.9 or newer.

    npm ci
    npm run build
    npm start -- --hostname 127.0.0.1

The application reads the latest published run per request. Reload an open tab after a new run is published. Development can use `npm run dev`. The optional `npm run engine -- [options]` script finds the active Conda Python, repository virtual environment, or the interpreter named by `SATIM_PYTHON`.

## Screens and operating scope

- **Overview and merchants.** Retained activity, outcome denominators, available payment values, prior-only expectations, intervals, incident state and planning forecasts. Partial monetary totals show missing-amount counts. Merchant health is a weighted operational checklist with a visible coverage fraction.
- **Alerts and incidents.** The Python engine supplies frozen V2 scores, B4 evidence, lifecycle and stable model IDs. The incident page adds evaluated triage criteria, impact estimates and scoped workflow actions.
- **Intelligence.** V3 collective warnings and V4 investigation candidates have separate views and evidence.
- **Transactions.** Card-free event rows with split/row traceability, status, channel, category, amount availability and contactless filters.
- **Simulator.** Deterministic planning arithmetic using the published forecast and archived hourly mix. Review cost assumptions apply to the frozen development outcome counts.
- **Assistant and reports.** Answers need the language model (`LLM_URL`); without it the assistant shows an error rather than a rule-based answer. The optional private HPC endpoint can assist with language and report composition. Standard PDFs print the current report page using local Chrome, Chromium or Edge. Browser print is available when a server-side browser is unavailable.
- **Data & runs.** Historical cutoff, generation time, frozen-config and input hashes, sealed parity, cleaning and development validation.

Accounts are local (see below). Signed sessions protect requests, and each account's pages and actions are checked on the server. The append-only ledger is scoped to one local server process.

## Sign in and accounts

There is one built-in account, the **administrator** (`admin`). On first start its password is `ADMIN_PASSWORD` if set, otherwise a random one written to `runs/admin-password.txt` (readable by the machine owner only). Change it on the Accounts page after signing in.

The administrator creates every other account on **Accounts** (`/admin`) and chooses:

- **Pages it can see:** any of Overview, Incidents, Alerts, Intelligence, Merchants, Transactions, Assistant, Simulator, Reports, Data & runs. Detail pages follow their list, the sidebar shows only those pages, and every other page or API call is refused on the server (`src/proxy.ts`).
- **What it can do:** *Review incidents* (comment, acknowledge), *Manage incidents* (assign, escalate, close, reopen), *Export* (CSV and PDF). Each write and export is checked again in its route (FR-05).

Only the administrator sees the audit ledger and manages accounts. Passwords are scrypt hashes in `runs/accounts.json`. Five wrong passwords lock the username for a minute. Editing an account or resetting its password signs out its open sessions. Every account change is written to the audit ledger.

## Your KPIs

Each account picks its own Overview cards with **Customize KPIs**. It starts with the default six. A card is a formula over named measures (`transactions`, `declined`, `accepted_value`, `alerts`, `merchants_flagged`, `open_incidents`, `days`…) with + − × ÷ and parentheses, e.g. `declined / transactions` or `accepted_value / accepted`. Each card is shown as a whole number, a decimal, DZD or a percent, with a line, area or bar chart of its daily values, or no chart. The formula is parsed into a tree and evaluated, never run as code, and checked again on the server (`src/lib/formula.ts`, self-test: `node src/lib/formula.test.ts`). The Overview filters apply to every card.

See the [API contract](../docs/ARCHITECTURE.md), [integration report and verification commands](../docs/INTEGRATION_REPORT.md), and [frontend handoff](../HANDOFF.md).

## Assistant design (FR-45–47)

- **Deterministic tools.** `src/lib/assistant.ts` holds the guards (refusals) and the read-only queries the model's tools run. It maps each question to one of a fixed set of queries over the snapshot: shortfall, declines, channels, incidents, forecast, summary, merchant explanation, health and next check. It makes no external call and needs no language model, and no free-form query ever reaches the data.
- **Refusals.** It refuses questions about intent or legality, any request for card data, and any write action (it is read-only). For "what caused…" questions it shows the evidence and states that the cause is not confirmed, listing the data needed to confirm it.
- **Language model (optional).** `src/lib/llm.ts` connects the assistant to Gemma 4 26B served on our HPC slice (contract and start-up: `../llm/README.md`). Set `LLM_URL` in `web/.env.local` (see `.env.example`) and open the tunnel with `../llm/tunnel.sh`. Order for every question:
  1. The rules' guards run first. Intent/legality, card-data and write requests are refused and never reach the model.
  2. The model sees the earlier turns of the conversation (last 6 questions and answers) and calls tools (at most 4 rounds, 8 s in all). The baseline tools (`llm/contract/tools.json`) run the deterministic assistant above; 9 app tools (`src/lib/assistant-tools.ts`) add day detail, incident detail, alerts, merchant comparison, what-if simulation (same code as the Simulator page, `src/lib/simulate.ts`), collective anomalies, engine quality, PDF reports and CSV exports. Every number still comes from the engine; arguments are allowlisted.
  3. The answer is checked: no prohibited term, and numbers must appear in the tool results, the question or the earlier (already checked) turns. Rounding a k/M amount is accepted; anything else is sent back once to be restated with the exact figures. The evidence links, table and scope line come from the tools, in the user's language.
  4. If the model is unset, unreachable, slow or its answer is rejected, the request fails with `503` (`model_off`, `model_offline` or `model_rejected`) and the chat shows the error. There is no substitute answer: rules written for this dataset could state wrong figures once the data changes, and an error is better than a false answer.
- **Model status.** `GET /api/v1/assistant/status` says whether the model is `online`, `offline` (configured but unreachable) or `off` (not configured), and every reply carries `model`. The chat shows a note above the composer when it is not online (with Retry), because the assistant cannot answer until the model is back. "this" / "hada" with nothing newly selected reuses the previous question's selection on the same page (also with the model).
- **Saved conversations.** Every turn is stored in `runs/conversations/<id>.json` (runtime state, owned by the signed-in account). The assistant page has a history rail (a drawer under 900 px): new conversation, open, delete with a confirm step, and a fold button that collapses it to the left (remembered in the `pai-rail` cookie, so the page renders folded without a jump); `/assistant?c=<id>` opens one directly. API: `GET /api/v1/assistant/conversations`, `GET|PATCH|DELETE /api/v1/assistant/conversations/{id}`; `POST /api/v1/assistant` takes `conversation_id`.
- **Filters follow the URL.** `FilterForm` is keyed by the query string, so a chart click, Back or a link rebuilds it and every field shows the filter actually applied. The overview's channel filter takes several channels (`channel=A,B`, comma-separated; also understood by the alerts and transactions lists). The Channels pie (a 3-D tilted disc in SATIM colours, `Pie3D` in `components/charts-client.tsx`, with each slice's exact share on a callout because a tilted pie distorts areas) keeps every channel visible and dims the ones outside the filter: click a slice for only that channel, Ctrl / ⌘ / Shift-click or tick a legend row to add or remove one, and "All channels ×" clears it; the Channel field shows "N channels selected".
- **Assistant on every page.** `components/assistant-dock.tsx` (mounted in the app layout, hidden on `/assistant`): a round button bottom-right opens a panel over the page (full screen on phones, Esc closes). Each question carries the current path and query; the server rebuilds that page's figures with `lib/page-context.ts` (one describer per page, panel names as on screen) and offers them to the model as the `page_context` tool, with a system line naming the page and its panels. Page-specific suggestions; the conversation follows the user across pages (the panel lives in the layout), is saved like any other with the page each question came from ("asked on …" on the full page), and opens on `/assistant` from the panel's expand button. Without the model, a question about "this chart/page" gets the page's deterministic summary. If a page's panels change, update its describer.
- **Movable panel, selections.** The panel (380 × 560) is dragged by its header; the position is kept in `localStorage` (`pai-dock-pos`) and a double-click on the header puts it back. Users can attach up to 4 parts of the page to a question (`components/page-select.tsx`): highlighted text gets an "Ask about this" button, and the crosshair in the composer starts pick mode (outline on hover, click to attach, Esc to cancel; links are not followed while picking). Each selection carries its panel title, visible text, chart tooltip and ISO date (`data-date` on chart bars), table row mapped to column names, and in-app links; `lib/selection.ts` validates it on the server and appends it to the question for the model (its figures count as known numbers). The new `day_detail` tool explains one day for a merchant or the network, for a selected bar or row. Selections are stored with the question and shown as chips on it.
- **Reports composed by the assistant.** `compose_report` (`lib/custom-report.ts`) takes a title and up to 12 ordered sections: kpis, activity, channel_mix, alerts (with optional explanations), incidents, incident, merchant, compare, top_declines, shortfall, forecast, network_signals, engine_quality, simulation, and text written by the model. Only the spec is stored (`runs/reports/<id>.json`, per account); every section is filled from the engine when rendered, and text sections are checked so they contain only figures from the data (a text section left empty, or a placeholder, makes the server hand the figures back first). The report page `/reports/<id>` (version chip, Undo, Download PDF) and a preview route without the app shell (`/embed/reports/<id>?v=`) render it with `components/report-document.tsx`. The answer shows a live preview of the version it produced; asking for a change ("drop the forecast", "put the summary first", "translate the titles") calls `compose_report` with `report_id`, which keeps the previous version (`POST /api/v1/reports/<id>/undo`). On the report page the floating assistant edits it in place and the page refreshes. The Reports page lists these reports under "Prepared by the assistant".
- **PDF reports.** `GET /api/v1/reports/pdf?type=daily|weekly|merchant|alerts|incident&incident=&date=&merchant=&from=&to=&severity=&channel=` or `?id=<report>` prints the Reports page brief to A4 with headless Chromium (`playwright-core`, the local Playwright browser; `PDF_CHROMIUM` to use another binary). Logged in the audit ledger like CSV exports. The Reports page has daily, weekly, merchant, alert and incident briefs and a Download PDF button; the assistant's `generate_report` tool links the same file. With no browser on the machine the route sends the user to the report with the print dialog open (`?print=1`).
  When a file is asked for (PDF, report, CSV, export) and the model answers without calling `generate_report` / `export_data`, it is asked once more with that tool imposed (named `tool_choice`); if it still fails, the reply links ready-made PDFs instead of a page summary. Rejections are logged as `[assistant] model answer rejected: …`.
